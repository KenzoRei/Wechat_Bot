# Codex audit of customer pickup plan rev 5

2026-11-20. Review of commit `5396627` against the code at `8f0cb8b`. Findings are numbered for the plan's append-only response protocol. This is an audit of the plan, not approval to implement it.

1. **[P1] Define and carry the proposed AI fields through both response contracts.** The plan says the LLM returns top-level `pickup_type` and `pickup_customer_name`, but `AIResponse` has neither field (`ai/base.py:32-69`), `parse_response` discards both (`ai/prompt_builder.py:505-530`), and both turn handlers persist only `extracted_fields` (`core/workflow_engine.py:390-396,1075-1083`; `core/kefu_turn_apply.py:1443-1452`). Thus the resolver and PDF cannot see the proposed output. Specify whether these values live in `extracted_fields` or in new typed `AIResponse` members, and explicitly map them into `session.collected_fields` before readiness, validation, confirmation, and artifact generation. If top-level, include `ai/base.py`, the parser, both response-format blocks, and both turn handlers in the implementation list. Add a parser-to-confirmation test on each channel.

2. **[P1] Excluding pickup rows from candidates alone does not enforce code-side resolution.** Kefu merges `extracted_fields` before checking `address_match` and skips address matching whenever a destination ID already exists (`core/kefu_turn_apply.py:1443-1452,1496-1503`); Smart Robot also merges an AI supplied `destination_address_id` (`core/workflow_engine.py:390-396,1075-1083`). The existing validator checks UUID existence and warehouse scope, but not candidate membership or `pickup_kind` (`core/pre_confirm_validators.py:631-660`). An AI-supplied ID for the general pickup row, a retention row, or historical `散客` can therefore bypass the resolver and its name/type checks. For new outbound submissions, strip or reject AI supplied pickup IDs, resolve them only from a validated pickup type, and validate the final `(pickup_type, pickup_kind, destination_address_id, pickup_customer_name)` combination before confirmation and again before execution. Historical requests must remain readable. Test direct-ID injection on both channels.

3. **[P1] A confirmation correction cannot currently replace an existing destination by ordinary field merging.** Kefu only calls `_address_decision` when `destination_address_id` is absent (`core/kefu_turn_apply.py:1496`); both Kefu and Smart Robot merge new fields over old ones rather than deleting old keys (`core/kefu_turn_apply.py:1451`; `core/workflow_engine.py:1075-1083`). A reply such as “不是自提，送到 X” would retain the pickup address unless the backend clears it *before* matching; the reverse switch can retain the delivery ID. D12 needs an explicit transition step on both channels that removes stale destination/name/type, then resolves the new mode, reruns readiness and validators, and renders a new confirmation. Do not rely on the LLM emitting `null`, since a merged null can also bypass the existing missing-destination branch. Cover both directions from `pending_confirmation`, including an address-pivot resume (`core/kefu_turn_apply.py:899-907`).

4. **[P1] The proposed per-message vocabulary backstop blocks valid multi-turn pickup and delivery corrections.** It compares the current user's message with the AI's classification, but a follow-up containing only a name (“张三”) has no pickup vocabulary while the session still represents a pickup. Conversely D12's delivery correction “不是自提，送到 X” contains `自提` while explicitly negating pickup. A company/address name containing `自提` also triggers a false positive. Limit lexical checks to a *newly stated* intent on this turn, handle negation and quoted/named-address text, and use the persisted mode plus an explicit revision signal for subsequent turns. Test these examples in both channels; a plain regex over each entire message is not a reliable gate.

5. **[P2] Resolve the retention inventory meaning before signing the plan.** The seed note says retention goods do not leave the warehouse (`db/migrations/V2__seed_catalog.sql:78-79`), but the current path classifies every `self_pickup` row with no `destination_warehouse_code` as a normal outbound (`handlers/uchoice/storage_txns.py:139-149`) and deducts its inventory. The plan preserves that behavior for both new and old retention requests. Confirm whether “留存” means removal from managed stock or stock that remains available in the source warehouse. If the latter, the storage transaction, completion, and invoice logic need a separate design; a PDF label alone cannot express the intended stock state.

6. **[P2] Make the migration identify rows by stable IDs and enforce the resolver's uniqueness assumptions.** The resolver assumes exactly one `customer` row globally and one `retention` row per source warehouse, while a nullable `pickup_kind` plus a value CHECK permits duplicates and inconsistent `charge_type` values. Backfill the four known seed IDs (`db/migrations/V2__seed_catalog.sql:78-80`, `db/migrations/V24__add_nj_warehouse.sql:40-44`) rather than matching editable labels, add partial uniqueness constraints or a fail-closed cardinality check, and constrain non-null kinds to `self_pickup`. Keep `散客`'s ID and all historical references. A new charge type is unnecessary for the stated fee behavior (`core/uchoice_rates.py:14`). V42 is the next migration number in this tree.

7. **[P2] Specify the chat and export data propagation at each renderer.** Kefu's pending-list arrow line is built in `core/kefu_turn_apply.py:139-150` from `destination_name` populated by `core/uchoice_context.py:227-237`; other pending candidates use the separate `destination` field (`core/uchoice_context.py:286-295,340-354`), and batch completion has its own `destination_label` (`core/completion_batch.py:281-289`). Confirmation and completion also have distinct destination sections (`core/confirmation.py:396-411,550-556,677-680,835-841`). Changing only `core/kefu_response_renderer.py` will not produce the mock-up across lists and confirmations. Define a shared pickup display fact derived from the original request fields and propagate it through these builders, including Smart Robot result messages. The invoice detail sheet currently exports the address row's company and address only (`core/uchoice_invoice_export.py:270-287`), so it will say `客户自提` with a blank address and omit the pickup person unless this is explicitly changed or accepted by the user.

8. **[P2] Pass the stored pickup type explicitly to PDF generation and pin the historical hash behavior.** The proposed PDF signature only adds `pickup_customer_name`, but banner choice and CJK gating require the request's `pickup_type`. Both artifact builders must pass that stored value (`handlers/uchoice/pdf_stub.py:128-134,185-191`). Kefu regenerates outbound PDFs from the origin session (`core/kefu_artifact_loader.py:40-60`) and checks the regenerated bytes against the enqueued hash (`core/kefu_delivery.py:234-273`), so old requests with no type key must take the exact existing drawing path. A no-key fixture should compare bytes before and after the change, not just visual appearance. The current consignee helper uses Helvetica (`core/uchoice_delivery_order.py:82-92`), so CJK drawing is needed for new pickup documents. The supplied one-page samples' pickup text and REMARK bar do not overlap the order number, signature area, or legal text; the longer retention line also fits. Still test the implementation on a multi-page order.

## Review state

The plan is **not ready for signatures** while findings 1-5 are unresolved. No production code was changed during this audit.

## Codex re-audit of plan rev 7 (commit `80d7c0a`, 2026-11-20)

Only remaining blockers are listed below. Findings 1-8 were addressed in the rev 7 plan and Claude response; the user's D13 and D14 resolve the inventory and invoice choices.

9. **[P1] Smart Robot can cancel a pickup before the proposed turn hook runs.** `workflow_engine.run_and_get_reply` calls `_maybe_pivot_to_add_address` before dispatching to `_handle_new_request` or `_handle_continuation` (`core/workflow_engine.py:69-87`); the proposed `apply_pickup_turn` runs only inside those handlers. If the AI emits `pickup_type=customer` with `unmatched_new_address` for the named address in the same message, the pre-dispatch pivot cancels the outbound and opens an address case (`core/workflow_engine.py:105-160`). D11 says pickup intent wins over that address. Gate the pivot on the *validated* pickup intent, or move pickup classification ahead of the pivot, and test an initial pickup request and a confirmation revision that each name an unmatched delivery address.

10. **[P1] The new final-combination rule would reject in-flight historical retention requests.** V42 marks the three existing retention IDs `pickup_kind='retention'`, while requests created before V42 have no stored `pickup_type`. The rev 7 rule says absent type requires a destination with no `pickup_kind` (`plan.md`, “Final-combination check”), and grants a historical exception only for `legacy` (`散客`). A pre-deploy outbound draft or pending confirmation pointing to a retention row would fail the new check after deployment, especially at the proposed pre-execution gate. Define a grandfather rule for *all* pre-change pickup rows, including retention, based on durable request provenance or a version/cutover marker; keep the rule fail-closed for newly created requests. Test confirmation and completion of old retention and `散客` requests across the migration.

11. **[P1] D11's ignored address has no defined path into confirmation.** D11 requires the confirmation to say which named delivery address was not used, but the rev 7 contract specifies only `pickup_type` and `pickup_customer_name` in `extracted_fields`; the resolver outputs only `destination_address_id` (`plan.md`, “Contracts and chokepoints”, “Resolver”, “Prompt”). No field or turn hook records the ignored address, and the shared pickup display fact is built only from type and name. Specify a bounded, sanitized ignored-address field (or equivalent structured evidence), its lifecycle through confirmation corrections, and both channel renderers. Test a pickup request that names a delivery address and a later revision that removes that address from the new confirmation.

**Re-audit state:** findings 9-11 block signature. No production code was changed during this re-audit.
